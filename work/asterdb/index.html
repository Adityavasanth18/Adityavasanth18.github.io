01 / The problem

The storage engine has to answer a deceptively small question: when a write succeeds, what exactly has been promised?

AsterDB implements its own write-ahead log, SSTable format, Bloom filters, manifests, snapshots, transactions, and compaction. It is a single-process systems project with its own storage implementation, not a wrapper around another database.

The constraint that shaped the design

Concurrent writers may finish their durability steps out of order. A snapshot still needs a contiguous, coherent visibility boundary.

02 / Engineering decisions

Where the design
becomes a contract.

01

Make durability precede visibility.

Writes reserve sequence ranges, complete the selected WAL durability step, then become visible in sequence order. Group commit shares a sync barrier across queued writers.

Tradeoff A shared durability barrier reduces fsync calls, but queueing can increase latency. Fewer syncs do not automatically mean higher throughput.

02

Publish storage state atomically.

Immutable tables are written and validated before a synced manifest makes them live. Recovery skips log entries already covered by the manifest sequence.

Tradeoff Correctness depends on file and directory sync ordering, as well as filesystem and hardware behavior.

03

Give snapshots a precise contract.

MVCC reads resolve the latest version at or below a snapshot. Transactions add read-your-writes and write-write conflict detection.

Tradeoff The contract is snapshot isolation, not serializability. Write skew remains possible.

03 / Failure behavior

Incomplete is different from corrupt.

Recovery can ignore an incomplete WAL tail after an interrupted write. A checksum failure in a complete record or SSTable is reported as corruption rather than silently accepted. The read-only inspector validates referenced tables without opening the database for mutation.

04 / Evidence

The result that did not become a speedup claim.

In the checked-in 16-thread write-only comparison, group commit reduced WAL fsync calls from 41,000 to 16,424. Throughput was slightly lower: 11,875 versus 11,407 operations per second. The useful result is durability amortization, with its queueing cost left visible.

05 / Limits & next steps

A boundary worth stating.

The engine is embedded and single-process, with no replication or failover. Tables are materialized in memory on open. Flush is synchronous; compaction is backgrounded. Sparse indexes are persisted, but block-level point-read seeks are not implemented.

What I would work on next

Block-oriented SSTable reads and oldest-snapshot-aware version pruning are useful next steps. Both would address concrete memory and retention limits in the current design.
